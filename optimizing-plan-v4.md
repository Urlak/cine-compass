# План развития cine-compass

**Версия:** 4  
**Дата:** 2026-11-10  
**Подход:** KISS — личный CLI-проект, рассчитанный прежде всего на владельца и, возможно, нескольких друзей.

## Цель проекта

Основная цель этого этапа — **добавить к каждому фильму согласованные английские семантические теги и на их основе сформировать точный, переносимый профиль зрительских предпочтений**.

Профиль должен быть полезен не только внутри `cine-compass`: его можно сохранить в Markdown и передать любой другой LLM как компактное описание вкуса пользователя.

Сокращение расходов `predict` — полезная, но вторичная задача. Не строить дополнительную инфраструктуру ради оптимизации, пока теги и профиль уже дают основную пользовательскую ценность.

## Принципы KISS

1. **Python считает и проверяет; LLM классифицирует и интерпретирует.**
2. Сначала реализовать минимальный полезный вариант, затем расширять по реальной необходимости.
3. Не строить инфраструктуру для гипотетической нагрузки: текущий масштаб — около тысячи фильмов и несколько пользователей.
4. JSON-файлов достаточно. Не добавлять базу данных, векторное хранилище, отдельный сервис, сложный кэш или интерфейс управления таксономией.
5. Не кэшировать быстрые детерминированные вычисления без измеренной причины.
6. Не смешивать исходные факты, нормализованные значения и выводы LLM.
7. Любая оптимизация должна учитывать не только токены, но и стоимость разработки и сопровождения.

## Этап 0 — Сохранить уже сделанные базовые исправления

Не переделывать завершённые работы. Проверить, что остаются рабочими:

- логирование токенов и latency в `usage.jsonl`;
- детерминированная проверка «фильм уже есть в библиотеке» перед `predict`;
- передача полной программной сводки вместо её обрезанной версии;
- замеры `thinking` для `predict`.

Если какой-то пункт уже реализован и проверен, считать его завершённым. Не расширять измерительную инфраструктуру без конкретного вопроса, на который она должна ответить.

## Этап 1 — Создать небольшой английский словарь тегов

**Таймбокс: один рабочий день.** Цель — рабочий словарь, а не идеальная кинотаксономия.

- Начать с **40–60 тегов суммарно**. Не добиваться одинакового количества тегов в каждой категории.
- Все `id` и `label` — на английском. Описания тоже на английском, чтобы словарь и промпт использовали один язык.
- Начать с категорий: `genre`, `mood`, `atmosphere`, `themes`, `pacing`, `narrative`, `style`.
- На каждый тег достаточно четырёх полей: `id`, `category`, `label`, `definition` (одно короткое предложение).
- `include_when`, `exclude_when` и примеры добавлять только для тегов, которые окажутся неоднозначными на пилоте.
- Модель выбирает только существующие ID. Не требовать ровно 10 тегов: ориентир 5–10 подходящих тегов на фильм, но меньше допустимо.
- Синонимы объединять. Новые теги не добавлять автоматически.
- Создать один файл `taxonomy.json` с `taxonomy_version`. Не переиспользовать существующий ID для другого смысла.

**Граница между категориями:** настроение (`mood`) — эмоциональный тон; атмосфера (`atmosphere`) — ощущение мира фильма; тема (`themes`) — идеи произведения; стиль (`style`) — художественная подача; повествование (`narrative`) — способ рассказа. Не создавать отдельные категории, пока пилот не покажет реальную необходимость.

Официальные жанры из Kinopoisk или исходного экспорта не заменять LLM-тегами. Их перевод в `genres_en` — отдельная необязательная задача на будущее, не блокирующая этот этап.

**Результат:** небольшой утверждённый словарь, который можно сразу проверить на реальных фильмах.

## Этап 2 — Небольшой пилот классификации

Взять **15–20 разнообразных фильмов**: разные десятилетия, страны и типы, популярные и малоизвестные, с подробными и короткими описаниями.

- Передавать ID, русское и оригинальное название, год, тип, имеющееся описание и доступные factual metadata.
- Не передавать личную оценку пользователя: классифицируется фильм, а не отношение владельца к нему.
- Просить вернуть структурированный JSON: `kinopoiskId`, `status`, список tag IDs.
- Допустимые статусы: `complete`, `partial`, `insufficient_data`.
- При нехватке сведений модель должна пропустить неподтверждённые характеристики, а не угадывать.
- Полностью проверить первые 10 результатов; остальные — выборочно. Все ошибки схемы и невалидные ID проверить обязательно.
- Повторно классифицировать 3–5 фильмов тем же prompt/model/taxonomy и посмотреть, насколько совпадают наборы тегов. Это диагностическая проверка, не отдельная система оценки.

**Минимальные критерии, чтобы продолжить:**

- не менее 98% ответов проходят schema validation (с учётом одного исправляющего retry);
- менее 1% возвращённых tag IDs не существует в словаре;
- существенная ручная правка нужна менее чем для 15% проверенных фильмов.

Доля `complete` и повторяемость тегов записываются как диагностические показатели. Если пилот явно показывает проблему, исправить определения или prompt и повторить небольшой пилот. Не запускать полную обработку, пока классификация явно ненадёжна.

Предложения отсутствующих понятий записывать в `data/tag_suggestions.jsonl` только по необходимости. Не строить автоматическую агрегацию и workflow регулярного review. Добавлять тег в словарь, только если реальный пробел повторяется минимум на трёх фильмах и это не синоним существующего тега.

## Этап 3 — Пакетно заполнить semantic cache

Создать отдельный `data/semantic_cache.json`. Не менять `library.json` и `enrich_cache.json` результатами LLM.

Для каждой записи достаточно хранить:

- `kinopoiskId`;
- `tags` — список tag IDs;
- `status`;
- `taxonomy_version`, `prompt_version` и `model`;
- простой fingerprint входа (название, год, описание и версии), чтобы понимать, когда результат нужно пересчитать.

**Обработка:**

- Начать с batch по 10–20 фильмов.
- Общую инструкцию и словарь передавать один раз на batch; для каждого фильма — только его данные и ID.
- Требовать отдельный результат для каждого `kinopoiskId`.
- Python проверяет, что все ID на месте, нет дублей и все tag IDs существуют в активном словаре.
- Сохранять результат после каждой партии. При повторном запуске пропускать уже обработанные записи с актуальными версиями.
- Повторно отправлять только отсутствующие или невалидные записи, а не всю партию.
- При обрезанном или некорректном ответе уменьшить размер партии, а не строить сложную систему ретраев.

**Контроль расходов:**

1. По пилоту и первой полноценной партии рассчитать среднюю стоимость обработки одного фильма.
2. Умножить её на число оставшихся фильмов и добавить небольшой запас.
3. Установить простой `SEMANTIC_ENRICHMENT_MAX_COST_USD` в `.env`.
4. Остановить обработку, если лимит достигнут. Не нужны пять отдельных калибровочных партий, сложные прогнозы и отчётность сверх фактических токенов/стоимости.

Продолжать factual enrich через Kinopoisk параллельно, насколько позволяет квота. Он не блокирует Semantic Enrichment. Если factual metadata или описание отсутствуют, разрешить `partial`/`insufficient_data`; не считать, что модель достоверно восстановила факты по одному названию.

**Результат:** отдельный, проверяемый и возобновляемый набор английских тегов для библиотеки.

## Этап 4 — Сформировать переносимый Taste Profile

Это основной пользовательский результат после Semantic Enrichment.

Реализовать простую функцию в `cinecompass/taste.py`, которая читает библиотеку и `semantic_cache.json`, а затем пересчитывает профиль при запуске. Для примерно тысячи записей hash-кэш не нужен.

Формировать один профиль с несколькими понятными срезами:

- общие характеристики библиотеки;
- характеристики фильмов с личными оценками;
- теги, чаще встречающиеся у высоко оценённых фильмов;
- теги, чаще встречающиеся у низко оценённых фильмов;
- сочетания тегов и несколько показательных фильмов.

Не путать частоту тега в библиотеке с предпочтением пользователя. Показывать количество примеров и покрытие данных; не делать сильных выводов по одному-двум фильмам. Учитывать только валидные теги; `partial` можно использовать с явной пометкой, `insufficient_data` — не использовать.

Создавать два простых результата:

- `data/taste_profile.md` — компактный профиль, который можно прочитать, скопировать или передать другой LLM;
- `data/taste_profile.json` — те же основные данные в структурированном виде для использования самим проектом.

Markdown-профиль должен быть самодостаточным: объяснять предпочтения, указывать ограничения и покрытие, включать конкретные примеры. Он не должен зависеть от знания внутренней структуры `cine-compass`.

`markdown.py` отвечает за форматирование; расчёты остаются в `taste.py`. Не создавать несколько Snapshot-файлов или отдельную инфраструктуру кэширования.

**Результат:** переносимый Taste Profile, полезный как внутри cine-compass, так и в других LLM-сценариях.

## Этап 5 — Использовать теги в функциях cine-compass

Начать с простого применения, не проектируя универсальный ranking engine.

- `stats` / `profile`: передавать Taste Profile и несколько примеров вместо повторного пересчёта точных агрегатов моделью.
- `recommend`: использовать теги как дополнительный сигнал для отбора и ранжирования кандидатов. Не исключать фильм только потому, что у него нет тегов или статус `partial`.
- Официальные жанры и LLM-теги хранить и показывать раздельно.

Сначала внедрить это в наиболее полезную операцию. Не нужно одновременно переписывать все команды, если можно проверить пользу на одной.

## Этап 6 — Сокращать `predict` только если это всё ещё оправдано

Это необязательная оптимизация, а не условие завершения основной цели проекта.

Если `predict` после предыдущих изменений всё ещё расходует слишком много токенов:

1. Взять **20–25 фильмов с известными личными оценками**. Целевой фильм исключить из всех входных данных и агрегатов, чтобы не было утечки.
2. Сравнить только два варианта: текущий full context и semantic shortlist.
3. Для внешнего фильма без semantic tags в библиотеке выполнить один LLM-вызов классификации по той же таксономии, затем Python выбирает похожие фильмы. Если классификация `unknown`/`insufficient_data`, использовать full context.
4. На выборке сравнить MAE, долю ошибок не более 1 балла и суммарные токены. Внешние фильмы без известной личной оценки не включать в MAE.
5. Использовать shortlist только если MAE хуже не более чем на 0.15, доля ошибок ≤1 балла ухудшается не более чем на 5 процентных пунктов, а входные токены сокращаются минимум в 3 раза. Для внешнего фильма учитывать стоимость обоих вызовов.

Если критерии не выполняются, оставить full context. Не строить кэш профилей внешних фильмов, несколько стратегий ranking или routing моделей заранее.

## Что сознательно не входит в V4

- Автоматическое создание и постоянное сопровождение большой таксономии.
- Перевод всех официальных жанров в английский — можно добавить позже отдельным небольшим mapping-файлом, если это понадобится.
- Hash-кэш Taste Profile, база данных, vector database, embeddings и отдельный сервис.
- Автоматическая агрегация и модерация `suggested_tags`.
- Несколько стратегий context ranking и сложный cold-start cache.
- Model routing и инфраструктура выбора модели на лету.
- Массовая переработка всех промптов и команд до проверки полезности тегов.
- Полный benchmark каждой операции, bootstrap confidence intervals и сложная статистическая инфраструктура.

## Критерий завершения основного этапа

Основной этап считается успешным, когда:

1. Рабочий английский словарь применяется последовательно.
2. Библиотека обработана пакетно, результаты сохранены отдельно от factual metadata и не теряются при перезапуске.
3. Python формирует `taste_profile.md` и `taste_profile.json` из оценок и тегов.
4. Markdown-профиль достаточно точен и компактен, чтобы использовать его как самостоятельный контекст в другой LLM.

Дальнейшая оптимизация `predict`, `recommend` и моделей выполняется только при наличии конкретной проблемы и ожидаемой выгоды, оправдывающей стоимость разработки и поддержки.

### Этап 6 (predict): решение — не трогать

Аудит проведён без изменений кода. Вариант semantic shortlist (35 фильмов, ~6–8 тыс. prompt-токенов, −87…−90 %) отклонён сознательно: ручные predict вызываются редко и прикрыты deterministic lookup (0 токенов для фильмов в библиотеке); экономия ~56 тыс. токенов/вызов окупает парный A/B-тест (~0.7 млн токенов) только после ~13 запросов; выборка benchmark мала (16 целей, MAE 1.06, ±1 = 0.81) для уверенной оценки дельты качества; покрытие тегами 47 %.

Full context остаётся baseline. Benchmark повторно не запускается. Вернуться к вопросу, только если: predict станет регулярным, появится интеграция с другими пользователями/сервисами, или стоимость полного контекста станет заметной.

Дальнейшая оптимизация — только по реальной потребности, не по умолчанию.
