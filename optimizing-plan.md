# План оптимизации cine-compass

Принцип: **Python определяет факты, LLM интерпретирует**. И второе правило: **не оптимизировать то, что нельзя измерить**.

---

## Фаза 0 — Измерительный фундамент (параллельно, ~1 день)

Без этого нельзя доказать, что последующие изменения не ухудшили качество.

- **Latency:** добавить `start_ts`/`end_ts` в `usage.jsonl`. Тривиально.
- **Benchmark для predict:** ретроспективная выборка. Python строит профиль по фильмам, просмотренным до даты X, скрывает оценку фильма после X, сравнивает прогноз с фактом. **Обязательно исключить тестируемый фильм из истории профиля** — иначе утечка. 20–30 названий, ~15 внутри библиотеки, ~15 вне. Метрики: MAE, доля ошибок ≤ 1 балла, $/запрос.
- **Baseline-замеры:** 10–20 живых вызовов текущей архитектуры на 3.8-flash. `usage.jsonl` уже пишется — накопить данные.
- **Цены:** если тариф известен — константы в `.env`. Если нет — считать в токенах, не в деньгах (cached ≠ бесплатно, нельзя строить архитектуру на предположении о работе implicit cache).

## Фаза 1 — Убрать очевидно лишнее (P0, ~1 день)

### A2. Детерминированный lookup в `predict` — **делать первым**

Сейчас `predict` сжигает 63 580 токенов, чтобы модель нашла совпадение по названию. Это устраняется кодом:

1. Нормализовать запрос (регистр, пунктуация, оригинал/русское).
2. Проверить `title`, `originalTitle`, при неоднозначности — год и `kinopoiskId`.
3. При однозначном совпадении — вернуть сохранённую оценку из `library.json`. **0 токенов, 100 % точность.**
4. Иначе — текущий путь через LLM.

Это не «экономия», а устранение целого класса ошибок: модель может не найти фильм, который в данных есть — гарантий нет.

### A1. Полная программная сводка в промпт

`_rows_and_overview` обрезает overview до 146 символов — модель пересчитывает агрегаты по 1155 строкам и ошибается (7.64 против 8.19). Передавать полный overview (~1.5K символов, ~500 токенов) во все четыре промпта.

**Важно:** это **не оптимизация расходов, а исправление точности**. Вход немного вырастет (+~500 токенов), но исчезнет источник фактических ошибок.

### A3. `thinking_budget=0` для `predict` — только после замера

В данных фигурируют два числа: 442 (живой `predict`) и 5 468 (ранний probe на `stats`). Это разные операции, переносить 5 468 на `predict` нельзя. Действие:

1. Замерить фактический thinking на 10 живых `predict` (уже есть `usage.jsonl`).
2. Если стабильно > 500 — выставить `0` и проверить на benchmark, что MAE не вырос.
3. Если < 500 — оставить динамический, экономия не стоит риска.

## Фаза 2 — Taste Snapshot и разделение контекста (P1, ~2–3 дня)

Ответ на главную проблему: все четыре операции получают одинаковый контекст, хотя решают разные задачи.

- Новая функция `build_taste_snapshot()` в `markdown.py`: агрегаты (жанры, десятилетия, средние, распределение оценок, топ режиссёров) + **репрезентативные примеры** по категориям. Кэшируется по хешу `library.json`.
- `stats` / `profile`: snapshot + полный `rows` (как сейчас). Здесь полный контекст оправдан — задача агрегатная.
- `recommend`: snapshot + **предфильтр кандидатов по режиму** (old/new/classics) на Python. Модель только ранжирует уже отфильтрованное.
- `predict`: пока без изменений — его сокращение в фазе 3, после enrich.

Низкий риск: snapshot — это данные, которые и так считаются в `build_catalog`, просто перестают выбрасываться.

## Фаза 3 — Сокращение контекста `predict` (P1, **после завершения enrich**)

**Условие запуска:** сейчас только 395 из 1155 записей имеют жанры. Префильтр на неполных данных будет систематически исключать релевантные примеры. Ждать завершения `enrich` (200/сутки, ~4 сессии).

После этого — сравнить на benchmark **два подхода**:

- **Similarity-based:** пересечение жанров, режиссёров, эпохи с запросом. Предсказуемо, но может недооценивать «вкусовые» сигналы.
- **Taste-based:** выбрать фильмы, лучше всего описывающие предпочтения зрителя (высокие оценки в разных жанрах, «почерк»), независимо от сходства с запросом.

Внедрять победителя. Целевой эффект: 63K → 8–12K токенов (в 5–8 раз).

## Фаза 4 — Structured output и программная валидация (P1, ~2 дня)

### Модель возвращает **ID, а не свободный текст**

- `recommend`: JSON `[{kinopoiskId, why_now, prep}]`. Python валидирует: принадлежность библиотеке, отсутствие дублей, отсутствие просмотренных, соответствие `count`. Для режима `classics` — отдельная логика (разрешены тайтлы вне библиотеки по условиям проекта).
- `predict`: `{score: int, reason: str}` с валидацией диапазона и парсингом.
- Регрессионные тесты на парсер + на отказ от невалидного вывода (сейчас корректность держится только на «дисциплине модели»).

Это закрывает пункт «LLM-вывод принимается без независимой проверки» и делает анти-галлюцинационный текст `STYLE` вспомогательным, а не единственным механизмом.
